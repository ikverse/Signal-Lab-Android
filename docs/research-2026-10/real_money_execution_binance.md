Scope note: everything below was checked against pages fetched on 2026-10-21/22. ## 1. Order endpoints and semantics (REST, WebSocket API, user data stream)

### Takeaway
`POST /api/v3/order` with `MARKET`, `LIMIT`, `LIMIT_MAKER`, `STOP_LOSS_LIMIT`, `TAKE_PROFIT_LIMIT` is unchanged in shape; the big 2025-26 changes are that successful order placements now cost 0 request weight (2026-04-02), the listenKey user-data stream was removed (2026-02-20) in favour of subscribing over the WebSocket API, and OCO lives at `POST /api/v3/orderList/oco` (the old `/api/v3/order/oco` is marked deprecated). For a once-a-day app, REST plus polling is enough; a user-data stream is optional.

### Cited Findings
- `POST /api/v3/order`: IP weight 1, unfilled-order count 1; "This adds 1 order to the `EXCHANGE_MAX_ORDERS` filter and the `MAX_NUM_ORDERS` filter." Mandatory parameters by type: LIMIT = `timeInForce, quantity, price`; MARKET = `quantity` or `quoteOrderQty`; STOP_LOSS = `quantity, stopPrice` or `trailingDelta`; STOP_LOSS_LIMIT = `timeInForce, quantity, price, stopPrice` or `trailingDelta`; TAKE_PROFIT = `quantity, stopPrice`/`trailingDelta`; TAKE_PROFIT_LIMIT = `timeInForce, quantity, price, stopPrice`/`trailingDelta`; LIMIT_MAKER = `quantity, price` (rejected if it would immediately take) — [Binance Spot REST: Trading endpoints](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/trading-endpoints)
- `quoteOrderQty` on MARKET orders "specifies the amount the user wants to spend (when buying) or receive (when selling)" in the quote asset; base quantity then depends on liquidity — [Trading endpoints](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/trading-endpoints)
- `newOrderRespType`: `ACK`, `RESULT`, `FULL`; MARKET and LIMIT default to `FULL`, other types to `ACK`. ### Inferences
- For a daily-close app that places a handful of orders a day, the user-data stream is not required; `GET /api/v3/order` (weight 4) and `GET /api/v3/account` (weight 20) after each placement give the same information with trivial weight. If the app ever wants the stream, `userDataStream.subscribe.signature` is the right method because it works with HMAC keys without a session logon; anything still using listenKey has been dead since 2026-02-20.
- The app's "safety stop checked first, exit at next open" model maps to either (a) a resting `STOP_LOSS_LIMIT` (counts as an algo order; `MAX_NUM_ALGO_ORDERS` is 5 per symbol on BTCUSDT/SOLUSDT) placed right after the entry fills, or (b) a daily check that sends a MARKET exit. Option (a) protects against intraday gaps between daily runs; option (b) is what the paper ledger simulates. An OCO (`orderList/oco`, unfilled count 2) can carry both the stop and a take-profit leg if a strategy has one.
- `MARKET` with `quoteOrderQty` is the simplest way to size in USDT and avoids LOT_SIZE rounding on entry; exits must use `quantity` (the exact base `free` balance rounded down to `stepSize`).

### Gaps
- The portal's trading-endpoints page is truncated in text fetches; the deprecated `/api/v3/order/oco` note text itself was not readable (only the "Deprecated" label). Removal date for that endpoint: none announced in 2025-26 entries read.
- `GET /api/v3/exchangeInfo` request weight was not re-verified on the current page (legacy value 20).

## 2. Signing (HMAC vs Ed25519 vs RSA), recvWindow, timestamp drift, idempotency and crash reconciliation

### Takeaway
Binance "highly recommend[s]" Ed25519 keys; HMAC-SHA256 still works everywhere on REST. Since 2026-01-15 the signed payload must be percent-encoded before signing or you get -1022. Idempotency rests on `newClientOrderId` ("unique among open orders"; a duplicate while the first is open is rejected with -2010 "Duplicate order sent."), and after a timeout you must query by `origClientOrderId` because -1007 means "execution status unknown".

### Cited Findings
- Security types: `NONE`, `TRADE`, `USER_DATA`, `USER_STREAM`. SIGNED endpoints need `timestamp` and `signature`; "If `recvWindow` is not sent, it defaults to 5000 milliseconds"; "Maximum `recvWindow` is 60000 milliseconds" — [General API information](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/general-api-information)
- Timing check as written: `if (timestamp < (serverTime + 1 second) && (serverTime - timestamp) <= recvWindow)` then process, else reject; the check runs again before forwarding to the engine — [General API information](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/general-api-information)
- Error texts: -1021 "Timestamp for this request is outside of the recvWindow." / "Timestamp for this request was 1000ms ahead of the server's time."; -1022 "Signature for this request is not valid."; -1007 TIMEOUT "Timeout waiting for response from backend server. Send status unknown; execution status unknown." — [Errors](https://developers.binance.com/docs/binance-spot-api-docs/errors)
- HMAC: HMAC-SHA-256 with the secret, hex output, case-insensitive. RSA: PKCS#8 keys only, RSASSA-PKCS1-v1_5 with SHA-256, base64, case-sensitive. Ed25519: base64, case-sensitive. "It is highly recommended to use Ed25519 API keys." — [General API information](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/general-api-information)
- 2025-04-29: features that required Ed25519 "will be opened to HMAC and RSA keys. Ed25519 is still recommended." 2025-12-17: "Payloads must be percent-encoded before signing, starting about 2026-01-15 07:00 UTC. Non-conforming requests get -1022" (enabled on testnet first) — [Changelog](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG)
- Testnet page on key types: Ed25519 "offers security comparable to 3072-bit RSA, with smaller signatures (88 bytes vs. 344 for RSA-2048) and faster signing"; RSA 2048-4096 accepted, PKCS#1 v1.5 only (no PSS) — [Spot Testnet](https://testnet.binance.vision/)
- Binance's own security guidance recommends asymmetric keys because "the private key used to create the signature does not need to be shared" — [How to Use API Keys Safely (Binance)](https://www.binance.com/en/square/post/276340)
- `newClientOrderId`: "A unique id among open orders. Automatically generated if not sent." "Orders with the same `newClientOrderID` can be accepted only when the previous one is filled"; otherwise rejected — [Trading endpoints](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/trading-endpoints)
- -2010 NEW_ORDER_REJECTED messages include "Duplicate order sent." (clOrdId already in use), "Account has insufficient balance for requested action.", "Market is closed.", "Order would trigger immediately.", "Order would immediately match and take."; -2011 "Unknown order sent."; -2013 "Order does not exist."; -2015 "Invalid API-key, IP, or permissions for action." — [Errors](https://developers.binance.com/docs/binance-spot-api-docs/errors)
- 2025-05-22 changelog: a new `recvWindow` check from 2025-06-06 counts rejections toward the unfilled order count — [Changelog](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG)
- `GET /api/v3/order` (weight 4) accepts `origClientOrderId`; `GET /api/v3/allOrders` (weight 20) accepts a 24-hour `startTime/endTime` window; `GET /api/v3/myTrades` with `orderId` costs 5 — [Account endpoints](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/account-endpoints)

### Inferences
- Key choice for the app: Ed25519 is the better fit for an Android client because the private key never leaves the device and Binance only holds the public key; Android Keystore does not natively generate Ed25519 keys (its StrongBox algorithm list is RSA/AES/EC P-256/HMAC), so the Ed25519 private key would have to be generated in software and wrapped with a Keystore AES key (see section 9). An HMAC secret is simpler but is a shared secret Binance also holds; both are workable, and Binance's recommendation is Ed25519.
- Clock drift: Android devices usually keep NTP time, but the rule `timestamp < serverTime + 1000` is unforgiving on the fast side. Pattern: call `GET /api/v3/time` once per run, keep `offset = serverTime - System.currentTimeMillis()`, sign with the corrected time, and on -1021 refresh the offset and retry once. `recvWindow` of 5000 is fine on a phone; raise toward 10000 only if mobile latency triggers -1021 repeatedly (never 60000 for orders).
- Idempotency pattern: derive `newClientOrderId` deterministically, e.g. `sl2-<strategyId>-<symbol>-<candleOpenMs>-<side>` (keep within Binance's client-ID length/charset; the length limit was not visible in the fetched text). Persist the intent (symbol, side, qty, clientOrderId, state=SENDING) in Room *before* the HTTP call. On any timeout/5xx/-1007, do not resend; query `GET /api/v3/order?symbol=..&origClientOrderId=..`: -2013 means it never reached the engine (safe to resend with the same ID), otherwise adopt the returned state. Because the same client ID cannot be reused while the first order is open, a blind retry cannot create a second live order (it would fail with "Duplicate order sent."), but a retry after a *filled* order would be accepted, which is why the local SENDING record must gate retries.
- Reconciliation on every run: `GET /api/v3/account?omitZeroBalances=true` (weight 20) for balances, `GET /api/v3/openOrders?symbol=` per tracked symbol (6 each) for resting stops, and `GET /api/v3/order` per locally-open intent. Compare `free + locked` of each base asset with the ledger's open positions; any unexplained balance or missing stop goes to a "needs attention" state and disables new entries for that symbol.

### Gaps
- The exact maximum length and allowed characters of `newClientOrderId` were not in the fetched text (legacy docs stated a regex and a 36-char limit; not re-verified).
- No official doc page on "how to reconcile after a crash" exists; the pattern above is composed from the endpoint semantics.

## 3. Key permissions and restrictions (IP whitelist, 90-day rule, sub-accounts, 2FA/KYC)

### Takeaway
The 2021 rule that unrestricted-IP keys lose "Enable Spot & Margin Trading" after 90 days was withdrawn as of 2023-10-24. Today: HMAC keys with unrestricted IP are read-only ("won't have any permission other than reading"); withdrawals always need an IPv4 whitelist; an unrestricted key inactive for 30 days is deleted. Self-generated (Ed25519/RSA) keys are Binance's stated alternative to IP restriction. Creating a key needs a verified (KYC) account with 2FA.

### Cited Findings
- "Note: The following API key permission rules are no longer applicable as of 2023-10-24." The withdrawn rule read: if the key "allows access to any IP address ... your selected 'Enable Spot & Margin Trading' permission will be valid for 90 days from the activation time" (published 2021-07-26, effective 2021-07-27, after a 30→90 day extension) — [Updates to API Key Permission Rules (2021-07-26)](https://www.binance.com/en/support/announcement/updates-to-api-key-permission-rules-2021-07-26-11e4c2f44e7a47b9b5fc0e479c0b256f)
- Current FAQ (last updated 20 March 2025): must "complete identity verification" and "enable two-factor authentication (2FA)"; key types: "System-generated" (HMAC) and "Self-generated" (Ed25519 or RSA, you supply the public key); "Unrestricted-IP-Access HMAC API Key(s) won't have any permission other than reading"; "Adding IP access (IPv4 format) restrictions is mandatory to enable withdrawal permission"; since 2023-01-30 system-generated key permissions can be "[Enable Reading]" only if IP is unrestricted; Binance "strongly recommend[s] against" enabling non-read permissions without IP restriction; alternatives named are self-generated keys or disabling default security controls — [How to Create API Keys on Binance](https://binance.com/en/support/faq/how-to-create-api-360002502072)
- "If your API key does not use a whitelisted IP and is inactive for 30 days, it will be deleted." "Binance strongly recommends users use IP whitelisting on all their API keys." Use one key per app with only the permissions it needs; never store keys in plain text or repositories — [How to Use API Keys Safely (Binance)](https://www.binance.com/en/square/post/276340)
- `GET /sapi/v1/account/apiRestrictions` returns `ipRestrict, createTime, enableReading, enableWithdrawals, enableInternalTransfer, enableMargin, enableFutures, permitsUniversalTransfer, enableVanillaOptions, enableFixApiTrade, enableFixReadOnly, enableSpotAndMarginTrading, enablePortfolioMarginTrading`; the only IP note is "You must apply the IP Access Restriction filter in order to enable withdrawals." No `tradingAuthorityExpirationTime` field is documented — [Get API Key Permission](https://developers.binance.com/docs/wallet/account/api-key-permission)
- Third-party reports of a 90-day expiry for non-whitelisted trading keys persist (QuantConnect forum; TradersPost) but predate or do not cite the 2023-10-24 withdrawal; Binance.US (a separate company) does reset inactive, non-whitelisted keys to read-only after 90 days — [QuantConnect forum](https://www.quantconnect.com/forum/discussion/12734/binance-demands-ips-for-api-connection-after-90-days/); [Binance.US API best practices](https://support.binance.us/hc/en-us/articles/16680337924631-Binance-US-API-keys-Best-practices-safety-tips)
- Sub-accounts: the Binance FAQ describes sub-accounts as open to verified users with 2FA, with regular users limited to five sub-accounts and higher caps by VIP level; sub-account volume counts toward the master's VIP level; "Managed sub-accounts" are VIP-only; sources conflict on caps — [Binance Sub-Account FAQ](https://www.binance.com/en/support/faq/binance-sub-account-functions-and-frequently-asked-questions-360020632811); [How to Become a Binance VIP](https://www.binance.com/en/support/faq/how-to-become-a-binance-vip-473a8456403c438e902d7b3048e49eb6)
- Master accounts can set/get/delete IP restrictions on sub-account API keys via `/sapi` endpoints — [Add IP Restriction for Sub Account API key](https://developers.binance.com/docs/sub_account/api-management/Add-IP-Restriction-for-Sub-Account-API-key)
- The Convert API page carries the generic API clause: "All users of this service are subject to the Binance Terms of Use"; the API is "not suitable for purposes including price arbitrage, high frequency trading, or price exploitation"; "Binance may restrict or terminate a Binance API connection at any time for any reason at its sole discretion" without prior notice — [Convert API Introduction](https://developers.binance.com/docs/convert/Introduction)

### Inferences
- A phone on mobile data has no stable IPv4, so an IP whitelist is impractical for the app itself. The documented paths that still allow trading without a whitelist are (a) a self-generated Ed25519/RSA key, or (b) an HMAC key with the default security control disabled. Ed25519 is therefore the natural choice on Android, and it also satisfies "never enable withdrawals" by construction (withdrawals cannot be enabled without an IP list).
- A trading key that never withdraws still exposes the account to "pump my bag" abuse if stolen (buying illiquid coins at bad prices), so the key must be treated as money, not as a read token.
- Isolation via a sub-account with only the trading capital is available to regular users (up to five sub-accounts per the FAQ), so the live-trading key can be scoped to a sub-account whose balance is the loss limit.

### Gaps
- Binance's global Terms of Use body text (eligibility, API/automation clauses) is rendered client-side and could not be fetched; only the Convert API's generic clause was readable. The maximum number of API keys per account was not confirmed.
- Whether the "disable default security controls" path still allows trading on an unrestricted HMAC key today was not confirmed beyond the FAQ wording.

## 4. Rate limits, bans and fees

### Takeaway
Live limits on 2026-10-21: 6000 request weight per minute per IP, 100 unfilled orders per 10 seconds and 200,000 per day per account, 300,000 raw requests per 5 minutes. A daily app uses a few hundred weight per run. Spot fees for a Regular User are 0.10% maker / 0.10% taker, 0.075% with BNB (25% off); USDC pairs show 0.095% taker.

### Cited Findings
- Live `rateLimits`: `REQUEST_WEIGHT` 6000 per 1 MINUTE; `ORDERS` 100 per 10 SECOND; `ORDERS` 200000 per 1 DAY; `RAW_REQUESTS` 300000 per 5 MINUTE — [live exchangeInfo](https://api.binance.com/api/v3/exchangeInfo?symbols=%5B%22BTCUSDT%22,%22SOLUSDT%22%5D); `RAW_REQUESTS` was raised to 300,000/5 min on 2026-04-02 — [Changelog](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG)

### Inferences
- Budget for one daily run over ~40 symbols: `exchangeInfo` once (legacy weight 20), `account` 20, `openOrders` 6 per symbol with open positions, a few `order` queries at 4, orders at weight 0 when successful. Even a hourly scan of 40 symbols' klines (weight 2 each in legacy docs) stays far below 6000/min. Per-run weight is not the risk; the risk is a retry loop after a 429, so the client must honour `Retry-After` and never retry a 418.
- The app's default cost assumption (0.25% round trip BTC/ETH, 0.40% others) is above the actual taker fee round trip (0.20%, or 0.15% with BNB) — the remainder is the implicit slippage budget. ## 5. Exchange filters and rounding

### Takeaway
Validate every order locally against `PRICE_FILTER` (tick), `LOT_SIZE` (step), `NOTIONAL` (min 5 USDT on BTCUSDT and SOLUSDT, applied to MARKET orders), `MARKET_LOT_SIZE` (maxQty), `PERCENT_PRICE_BY_SIDE` (for limit prices) and the open-order caps (`MAX_NUM_ORDERS` 200, `MAX_NUM_ALGO_ORDERS` 5, `MAX_NUM_ORDER_LISTS` 20). Round *down* quantities to `stepSize` and prices to `tickSize` with exact decimals; -1111 and "Filter failure: ..." are the symptoms of getting it wrong.

### Cited Findings
- `PRICE_FILTER`: `price >= minPrice`, `price <= maxPrice`, `price % tickSize == 0` (a 0 value disables that rule). `LOT_SIZE`: `quantity >= minQty`, `quantity <= maxQty`, `quantity % stepSize == 0` (also applies to `icebergQty`). `MARKET_LOT_SIZE`: same three rules for MARKET orders. `NOTIONAL`: `price * quantity >= minNotional` and `<= maxNotional`; `applyMinToMarket`/`applyMaxToMarket` decide whether each bound applies to MARKET orders; for MARKET orders the notional uses the reference price if present, else the average price over `avgPriceMins`, else the last price if `avgPriceMins` is 0. `PERCENT_PRICE_BY_SIDE`: BUY `price <= avg * bidMultiplierUp` and `>= avg * bidMultiplierDown`; SELL `price <= avg * askMultiplierUp` and `>= avg * askMultiplierDown`. `MAX_NUM_ALGO_ORDERS` counts `STOP_LOSS, STOP_LOSS_LIMIT, TAKE_PROFIT, TAKE_PROFIT_LIMIT`. `MAX_NUM_ORDER_LISTS` counts open lists (an OTOCO is one). `TRAILING_DELTA` bounds for each type/side — [Filters](https://developers.binance.com/docs/binance-spot-api-docs/filters)
- Live BTCUSDT: `PRICE_FILTER` tickSize 0.01 (min 0.01, max 1,000,000); `LOT_SIZE` minQty 0.00001, maxQty 9000, stepSize 0.00001; `MARKET_LOT_SIZE` minQty 0, maxQty 144.69219062, stepSize 0; `NOTIONAL` minNotional 5.00, `applyMinToMarket true`, maxNotional 9,000,000, `applyMaxToMarket false`, `avgPriceMins 5`; `PERCENT_PRICE_BY_SIDE` bidMultiplierUp 1.2, bidMultiplierDown 0.5, askMultiplierUp 2, askMultiplierDown 0.8, avgPriceMins 5; `MAX_NUM_ORDERS` 200; `MAX_NUM_ORDER_LISTS` 20; `MAX_NUM_ALGO_ORDERS` 5; `MAX_NUM_ORDER_AMENDS` 10; `ICEBERG_PARTS` 100; `TRAILING_DELTA` 10-2000 both sides — [live exchangeInfo](https://api.binance.com/api/v3/exchangeInfo?symbols=%5B%22BTCUSDT%22,%22SOLUSDT%22%5D)
- Live SOLUSDT: tickSize 0.01 (max 10,000); `LOT_SIZE` minQty 0.001, stepSize 0.001, maxQty 90,000; `MARKET_LOT_SIZE` maxQty 90,303.19; `NOTIONAL` min 5 USDT applied to market; other caps identical to BTCUSDT — [live exchangeInfo](https://api.binance.com/api/v3/exchangeInfo?symbols=%5B%22BTCUSDT%22,%22SOLUSDT%22%5D)
- `exchangeFilters` is empty on the live exchange (no exchange-wide `EXCHANGE_MAX_NUM_ORDERS` in force) — [live exchangeInfo](https://api.binance.com/api/v3/exchangeInfo?symbols=%5B%22BTCUSDT%22,%22SOLUSDT%22%5D)
- Error texts: -1111 "Parameter '%s' has too much precision."; -1013 "Filter failure: PRICE_FILTER" (price too high/low/off tick), "Filter failure: LOT_SIZE", "Filter failure: NOTIONAL", "Filter failure: MIN_NOTIONAL", "Filter failure: PERCENT_PRICE_BY_SIDE", "Filter failure: MARKET_LOT_SIZE", "Filter failure: MAX_NUM_ORDERS", "Filter failure: MAX_NUM_ALGO_ORDERS" — [Errors](https://developers.binance.com/docs/binance-spot-api-docs/errors)
- 2026-02-24 changelog: `ICEBERG_PARTS` set to 100 on 2026-03-12; 2025-09-29: `MAX_ASSET` filter documented (visible only via `GET /api/v3/myFilters`) — [Changelog](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG); [Account endpoints](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/account-endpoints)

### Inferences
- Rounding recipe (BigDecimal, never Double): `qty = floor(rawQty / stepSize) * stepSize`, formatted with exactly the number of decimals in `stepSize` (strip trailing zeros is fine, extra digits are not); `price = round-to-tick` using floor for BUY limits / ceil for SELL limits if you want to stay inside PERCENT_PRICE_BY_SIDE; then check `qty >= minQty` and `qty * refPrice >= minNotional * (1 + margin)` with a few percent of margin because the engine uses its own 5-minute average/reference price, not your last close. For `quoteOrderQty`, use the quote asset's precision from `exchangeInfo` (`quoteAssetPrecision`, 8 on USDT pairs) and keep the amount ≥ minNotional.
- Minimum order size in USDT: `minNotional` is 5 USDT on both sampled pairs and `applyMinToMarket` is true, so a market order below 5 USDT is rejected. Practical floors are higher: on BTC the step 0.00001 BTC ≈ 1.07 USDT at ~107k, so a 20 USDT order can only be sized to the nearest ~1 USDT; on SOL step 0.001 ≈ 0.2 USDT. A 1,000 USDT account running four 250 USDT positions is far above the exchange floor; the real constraint is fee drag, not `minNotional`.
- `MAX_NUM_ALGO_ORDERS` = 5 per symbol: if the app ever stacks several strategies on one coin each with its own resting stop, it hits this cap at six. One stop per symbol (aggregate position) or in-app stop checks avoid it.
- Filters change (reference-price regime since 2026-05-08), so re-pull `exchangeInfo` for the traded symbols at the start of every live run rather than caching for days.

### Gaps
- Per-coin `minNotional` across the whole top-40 USDT universe was not pulled (only BTCUSDT and SOLUSDT); the app should read it live rather than hardcode.
- `quoteAssetPrecision` / `baseAssetPrecision` values were not extracted from the live call.

- Testnet order books are thin and prices do not track production, so fills and slippage there are meaningless; use `POST /api/v3/order/test` with `computeCommissionRates=true` against **production** for a zero-risk dry run of filter validation and fee preview on real prices.

### Gaps

## 7. Slippage and liquidity at the daily open (00:00 UTC)

### Takeaway
For BTC-USDT on Binance, $500-$10,000 market orders are far inside the top of book (about $16M bid / $26M ask within 1% of mid in Dec 2025) and cost roughly the spread. For rank-30-40 alts, Binance-specific depth was not found; cross-exchange top-50 alt depth was ~$700M aggregate in Q1 2025. The hour boundary, and 00:00/08:00/16:00 UTC in particular, shows a measurable volatility/volume burst in the first minute; a delay of a few minutes avoids it at the cost of entering off the official open print.

### Cited Findings
- Binance BTC-USDT spot order book snapshot (1 Dec 2025, midprice ~$96,624): "$16 million on the bid side and $26 million offered within 1% of the midprice"; Binance processed $20B spot volume and 61.9M trades that day; "Average trade size is below $1,000"; BTC-USDT 1% depth "eclipsed $600 million on Binance" at the October 2025 record high; spreads "at or near one tick most hours" in 2020-21 and "minimal" during active hours (qualitative). Kaiko report produced "in partnership with" Binance — [Kaiko: Liquidity Flywheel Drives Binance to 300 Million Users (PDF)](https://resources.kaiko.com/hubfs/Liquidity%20Flywheel%20Drives%20Binance%20to%20300%20Million%20Users.pdf)
- Kaiko spread cheat-sheet (1 June 2023): quoted spread = (best ask − best bid)/mid; "2 bps = 0.02%"; BTC-USDT and ETH-USDT on Binance are "extremely tight" and Binance has the best BTC/ETH spreads; SOL and XRP spreads on TUSD pairs "range from 8 bps and above"; spreads widen in volatility as market makers hedge — [Kaiko: A cheatsheet for bid-ask spreads](https://www.kaiko.com/resources/a-cheatsheet-for-bid-ask-spreads)
- Kaiko Q1 2025 (via Cryptopolitan): the altcoin market lost 30% of its 1% market depth; "the top 50 assets based on market cap erased 300M in liquidity, starting from about $1B"; ETH 1% depth fell to $243M by 6 April 2025 (cross-exchange figures) — [Cryptopolitan on Kaiko Q1 2025](https://www.cryptopolitan.com/kaiko-q1-report-bitcoin-retains-liquidity-ethereum-and-altcoins-lost-market-depth/)
- Periodicity paper (Binance BTC/USDT, ETH/USDT; Coinbase Pro; Uniswap V2; 2019-2021): "Notice the spikes in volume and volatility at 0h and 16h, and less noticeable spikes at 8h"; "There is a large burst in volatility during the first minute of the hour", medium bursts after minutes 15/30/45, strongest "every fourth hour, 00h,…,20h, with the exception of 08h"; "On Binance, the funding takes occur at 00h, 08h, and 16h"; "The 1st hour and the hour after 16:00 UTC tend to have the highest level of volatility", "particularly large on Mondays"; on Binance "the relative illiquidity is largest during night time in East-Asia where it is about 30% larger"; weekends calmer, "most pronounced on Saturdays"; "These patterns have grown stronger over the years" — [Periodicity in Cryptocurrency Volatility and Liquidity (arXiv 2109.12142)](https://arxiv.org/abs/2109.12142)
- Binance MARKET orders have no price, so the notional/percent-price checks use the reference or 5-minute average price; `MARKET_LOT_SIZE` caps a single market order at 144.69 BTC / 90,303 SOL on the sampled pairs — [Filters](https://developers.binance.com/docs/binance-spot-api-docs/filters); [live exchangeInfo](https://api.binance.com/api/v3/exchangeInfo?symbols=%5B%22BTCUSDT%22,%22SOLUSDT%22%5D)

### Inferences
- Cost of a market order ≈ half-spread + impact. BTC/ETH-USDT: with one-tick spreads and tens of millions within 1%, a $10,000 taker order moves through well under 0.05% of the 1% book; expect ~0-2 bps beyond the fee. Top-40 alts: if the top-50 aggregate is ~$700M across all exchanges, the average is ~$14M per asset (both sides, all venues) and the lower-ranked names hold far less; assuming Binance carries a large share and a roughly even distribution, a rank-30-40 USDT pair plausibly has $1-5M per side within 1%. A $2,000 order is then ~0.05-0.2% of the 1% book (negligible impact, cost ≈ spread of maybe 5-15 bps); a $10,000 order is ~0.2-1% of it, so a few bps of impact on top. These are back-of-envelope figures; the app's 0.40% round-trip assumption for alts covers them at these sizes, but not for $10,000 orders in the thinnest names in the universe.
- 00:00 UTC is the worst minute to send a market order in the cycle: it is simultaneously the daily candle boundary and a Binance funding timestamp, and the paper shows the first-minute burst is strongest at the four-hourly marks. Waiting 2-5 minutes after the open trades the burst for a small, random deviation from the candle's official open price. The paper ledger assumes entry at the open print; a live run that enters at 00:03 should record the actual fill and the open print separately so the realised-vs-assumed gap is measured, not assumed. Alternatively a `LIMIT_MAKER` at the open price (or a `LIMIT` IOC a few bps through the touch) avoids paying the taker spread but may not fill.
- Spreads widen during stress; the cost model should be per-coin and ideally per-fill (from `myTrades`), not a constant.

### Gaps
- No Binance-specific, time-of-day spread/depth table for top-40 USDT pairs around 00:00 UTC was found in public Kaiko/Binance Research material; Kaiko's hour-of-day data is behind its data products. The $500/$2,000/$10,000 cost figures above are inferred from depth, not measured.
- The periodicity paper's data ends June 2021; a 2024-26 replication with Binance order-book data was not found.

## 9. Android-side safety patterns for holding a trading key and running once-a-day orders

### Takeaway
Keep the signing secret in (or wrapped by) an Android Keystore key that is hardware-backed (StrongBox where available), require `BIOMETRIC_STRONG` auth-per-use through `BiometricPrompt` + `CryptoObject` to unlock it, exclude the encrypted blob from cloud backup and device transfer, keep the daily job on an `AllowWhileIdle` exact alarm plus a WorkManager fallback, and make every order path idempotent with a local intent log and a hard kill switch. The app's existing Keystore-backed key storage and certificate pinning carry over; note that Jetpack `EncryptedSharedPreferences` was deprecated in April 2025.

### Cited Findings
- Keystore: "Key material never enters the application process ... If the app's process is compromised, the attacker might be able to use the app's keys but can't extract their key material." With secure hardware "its key material is never exposed outside of secure hardware. If the Android OS is compromised ... it can't extract them from the device." — [Android Keystore system](https://developer.android.com/privacy-and-security/keystore)
- StrongBox: "Devices running Android 9 (API level 28) or higher can include a StrongBox KeyMint"; check `FEATURE_STRONGBOX_KEYSTORE`, then `setIsStrongBoxBacked(true)`; on `StrongBoxUnavailableException` "generate or import the key without calling `setIsStrongBoxBacked(true)`"; supported: RSA 2048, AES 128/256, ECDSA/ECDH P-256, HMAC-SHA256; "it is slower, more resource-constrained, and supports fewer concurrent operations. For most apps, StrongBox is not necessary." Check placement with `getSecurityLevel()` (`TRUSTED_ENVIRONMENT` or `STRONGBOX`) on API 29+ — [Android Keystore system](https://developer.android.com/privacy-and-security/keystore)
- User-auth binding: keys can be "only authorized to be used if the user has been authenticated"; two modes: authorize for a time window, or "Each operation involving a specific key must be individually authorized by the user"; credential types `AUTH_BIOMETRIC_STRONG`, `AUTH_DEVICE_CREDENTIAL`; "If a key only supports biometric credentials, the key is invalidated by default whenever new biometric enrollments are added" (`setInvalidatedByBiometricEnrollment`); verify enforcement with `KeyInfo.isUserAuthenticationRequirementEnforcedBySecureHardware()` — [Android Keystore system](https://developer.android.com/privacy-and-security/keystore)
- BiometricPrompt: `BIOMETRIC_STRONG` = Class 3 biometric; `BIOMETRIC_WEAK` = Class 2; `DEVICE_CREDENTIAL` = PIN/pattern/password; `CryptoObject` supports `Signature`, `Cipher`, `Mac`, `KeyAgreement`; "If your app uses a secret key that requires biometric credentials to unlock, the user must authenticate their biometric credentials each time before your app accesses the key" (`setUserAuthenticationRequired(true)`, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`); for timeout-based keys "you can't pass an instance of `CryptoObject` into the `authenticate()` method"; catch `UserNotAuthenticatedException` and re-prompt; `BiometricManager.canAuthenticate()` codes incl. `BIOMETRIC_ERROR_NONE_ENROLLED` — [Biometric authentication dialog](https://developer.android.com/identity/sign-in/biometric-auth)
- Backups: Auto Backup includes shared prefs, `getFilesDir()`, databases, external files dir by default; excludes `getCacheDir()`, `getCodeCacheDir()`, `getNoBackupFilesDir()`; 25 MB quota; Android 12+ uses `android:dataExtractionRules` with `<cloud-backup>` and `<device-transfer>` sections (plus `android:fullBackupContent` for API ≤ 30); `<exclude domain="sharedpref|file|database|..." path="..."/>`; "If there are no rules for a particular backup mode ... that mode is fully enabled"; `disableIfNoEncryptionCapabilities` stops cloud backup on devices without a lock screen; "To back up user credentials and authentication tokens, don't store them in shared preferences or a file" — [Back up user data with Auto Backup](https://developer.android.com/identity/data/autobackup)
- Jetpack Security: `androidx.security:security-crypto` 1.1.0-alpha07 (9 April 2025): "Deprecated all APIs in favour of existing platform APIs and direct use of Android Keystore"; 1.1.0 stable shipped 30 July 2025 — [Security release notes](https://developer.android.com/jetpack/androidx/releases/security)
- Doze: "Suspends network access", "Ignores wake locks", "Defers standard AlarmManager alarms, including setExact() and setWindow(), to the next maintenance window", "Doesn't let JobScheduler run. WorkManager uses JobScheduler internally, so WorkManager tasks don't run"; "Neither setAndAllowWhileIdle() nor setExactAndAllowWhileIdle() can fire alarms more than once per nine minutes, per app"; "Alarms set with setAlarmClock() continue to fire normally. The system exits Doze shortly before those alarms fire"; apps may request `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` only for acceptable cases; "Task automation app" is listed as Acceptable; "Google Play policies prohibit apps from requesting direct exemption ... unless the core function of the app is adversely affected" — [Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)
- Exact alarms: apps targeting Android 12+ need `SCHEDULE_EXACT_ALARM` (user-grantable, revocable) or, from Android 13, `USE_EXACT_ALARM` (auto-granted, "Limited use cases", subject to Play policy); check `canScheduleExactAlarms()`; "When the `SCHEDULE_EXACT_ALARM` permission is revoked for your app, your app stops, and all future exact alarms are canceled"; `SCHEDULE_EXACT_ALARM` is not pre-granted to fresh installs targeting Android 13+ and is denied after backup-restore onto Android 14; `setExactAndAllowWhileIdle()` fires "at a nearly precise time ... even if battery-saving measures are in effect"; "Add randomness (jitter) to any network requests that trigger as a result of a repeating alarm" — [Schedule alarms](https://developer.android.com/develop/background-work/services/alarms/schedule)
- OWASP MASVS-STORAGE lists the weaknesses "Cryptographic Keys Stored Outside of Platform Keystore" (MASWE-0003), "Insertion of Sensitive Data into Logs" (MASWE-0005), "Sensitive Data Not Excluded From Backup" (MASWE-0006) and the practices "Exclude Sensitive Data from Backups" (MASTG-BEST-0004), "Remove Logging Code" (MASTG-BEST-0002) — [OWASP MASVS-STORAGE-1](https://mas.owasp.org/MASVS/controls/MASVS-STORAGE-1/)
- Binance-side controls that complement device security: one key per purpose with minimal permissions, never withdrawals; inactive unrestricted keys are deleted after 30 days; Ed25519/RSA keep the signing secret on your side — [How to Use API Keys Safely](https://www.binance.com/en/square/post/276340); [How to Create API Keys](https://binance.com/en/support/faq/how-to-create-api-360002502072)

### Inferences
- Key layout: generate an AES-256-GCM Keystore key `sl2.trade.kek` with `setUserAuthenticationRequired(true)`, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`, `setIsStrongBoxBacked(true)` with fallback, `setInvalidatedByBiometricEnrollment(true)`. Use it to wrap the Binance secret (HMAC secret or Ed25519 private seed) stored as a blob in `getNoBackupFilesDir()`. Since StrongBox cannot hold Ed25519 directly and TEE support for Ed25519 is not documented, the Ed25519 signing happens in-process with a seed that is unwrapped only after biometric auth; the raw seed exists in app memory only during the run.
- Auth-per-use vs unattended daily runs are in tension: a key that needs a fingerprint per use cannot sign at 00:02 while the owner sleeps. Two workable designs: (a) *Armed window*: the owner authenticates in the evening, which unwraps the secret into a separate Keystore AES key with `setUserAuthenticationParameters(T, ...)` or into process memory for the next run only, and the arm expires after 24h; (b) *Notify-then-confirm*: the alarm computes the orders, posts a high-priority notification, and the owner confirms with biometrics before anything is sent (losing the "at the open" timing but keeping per-order consent). The paper ledger already runs at the close, so (a) matches the current flow; (b) is the conservative first version.
- Backups/sync: exclude the wrapped blob, the intent log and the preferences holding the live-trading flag from both `<cloud-backup>` and `<device-transfer>`; a Keystore-wrapped blob restored onto another device is undecryptable anyway, but excluding it avoids a stuck "armed" state after restore. The app's existing Drive device-sync must never carry the trading key or the live flag.
- Scheduling: keep the existing daily alarm as `setExactAndAllowWhileIdle` (Doze allows it, once per 9 minutes per app, which suits a daily run) or `setAlarmClock` if minute-level precision matters; enqueue a WorkManager `OneTimeWorkRequest` with a network constraint as a fallback that reconciles if the alarm path failed; declare `SCHEDULE_EXACT_ALARM` (user-revocable, so check `canScheduleExactAlarms()` each run and degrade to "paper only" if revoked). If the device is offline at the alarm, the run must be marked missed rather than executed late with stale signals — or executed only within a configurable grace window (e.g. 15 minutes after the open).
- Network retries without duplicates: OkHttp's default `retryOnConnectionFailure` can resend a POST; disable it for order calls and implement the explicit SENDING → query → resolve state machine from section 2. Keep `recvWindow` small so a delayed duplicate is rejected by Binance as -1021 rather than executed.
- Kill switch and limits (app-side, since Binance has no account-level daily-loss limit): a global `liveTradingEnabled` flag checked at the top of every run and before every order; a per-day realised-loss cap and a per-day order-count cap; a per-symbol max notional; auto-disable on any unexplained balance mismatch, on -2015 (key/permission problem), on 418, or when `canTrade=false`. Reconcile against `GET /api/v3/account` and `openOrders` before placing anything.
- Pinning: Binance's public endpoints rotate certificates and use public CAs, so pin the CA/SPKI set (or rely on system trust with network-security-config `cleartextTrafficPermitted=false`) rather than a leaf; the self-made cert pin for the PC host is a different trust domain and should not be in the same pin set.

### Gaps
- Android docs do not state outright that Keystore keys are excluded from backups; this follows from "key material never exposed outside of secure hardware" and was not quoted verbatim. OWASP MASTG body text could not be fetched (navigation-only render).
- The Jetpack release notes name no replacement API; the recommendation is direct Keystore use.

## 10. Realism: what retail systematic crypto traders earn, and the arithmetic of a 0.5-1% edge

### Takeaway
The best population evidence (BIS Bulletin 69, Feb 2023) says a majority of crypto-app users in nearly every economy lost money on bitcoin, with the median user down about half by Dec 2022 under the BIS model, and that retail bought while large holders sold around Terra/FTX; account-level studies (eToro, German bank data) show retail chases momentum in crypto and trades more actively after adopting it. A genuine 0.5-1% net edge per trade at 2-4 trades a week is worth roughly $100-$2,000 a year on $1,000-$20,000 at prudent sizing, needs 400-1,600 trades to be statistically visible, and is dominated by position sizing: half-Kelly cuts the chance of a 50% drawdown from 50% to 12.5% while keeping 75% of the growth.

### Cited Findings
- BIS Bulletin 69 (Cornelli, Doerr, Frost, Gambacorta, 20 Feb 2023): "a majority of crypto app users in nearly all economies made losses on their bitcoin holdings" (data Aug 2015-Dec 2022); around Terra/Luna and FTX, "large and sophisticated investors selling and smaller retail investors buying"; "the market turmoil in 2022 had little discernible impact on broader financial conditions outside the crypto universe" — [BIS Bulletin 69](https://www.bis.org/publ/bisbull69.htm)
- Secondary summaries of the same bulletin: dataset of downloads/active use of 200+ exchange apps in 95 countries, 1 Aug 2015-15 Dec 2022; model assumes each new user invested $100 at download and the same monthly; estimated average loss $431 per investor (47.89% of $900 invested); 75% of new users downloaded an app after bitcoin passed $20,000 in Dec 2020; whales (>1,000 BTC) sold before sharp drops while 1-1,000 BTC holders added; "the median retail investor lost about half their investment by Dec. 2022" — [Ecofin Agency on BIS 69](https://www.ecofinagency.com/finance/1104-44420-bitcoin-retail-investors-lost-47-89-of-invested-funds-on-average-bis-bulletin); [The Block on BIS 69](https://www.theblock.co/news/regulation/2023-02-20-majority-of-bitcoin-retail-investors-lost-money-in-the-last-seven-years-bis-213372)
- Kogan, Makarov, Niessner, Schoar, "Are Cryptos Different? Evidence from Retail Trading" (JFE 2024; ~200,000 eToro accounts, 2015-2019): retail traders "are contrarian in stocks and gold, yet the same traders follow a momentum-like strategy in cryptocurrencies"; differences not explained by individual characteristics, fees, inattention or lottery preference — [NBER w31317](https://www.nber.org/papers/w31317)
- Hackethal, Hanspal, Lammer, Rink, "The Characteristics and Portfolio Behavior of Bitcoin Investors" (Review of Finance 2022, bank administrative data): "cryptocurrency investors are active traders who are prone to investment biases and hold risky portfolios"; after first purchase "the average cryptocurrency investor substantially increases account logins and trading activity" and tilts "toward even more risky securities" — [Review of Finance article](https://academic.oup.com/rof/article/26/4/855/6265330)
- Galaxy Research (Polymarket, prediction markets, not spot crypto): 69% of retail accounts lost money; the middle half sat between a small loss and a small gain — [Crypto Briefing on Galaxy Research](https://cryptobriefing.com/galaxy-research-polymarket-retail-losses/)
- Monte Carlo study of 378 non-stablecoin tokens (arXiv, Dec 2025): at 731-1095-day horizons the median excess return is −28.4% while the top quartile mean is +1326.7% (simulation, not accounts) — [arXiv 2512.02029](https://arxiv.org/pdf/2512.02029)
- Fractional Kelly (Geboers & Depaire, Entropy 2023): with f* = m/s² under GBM, "Considering a full Kelly position, the probability of experiencing a 50% drawdown is 50%"; "Assuming a half Kelly position, the probability of experiencing a loss of 50% drops to 12.5%"; growth ratio g(cf*)/g(f*) = c(2 − c), so half Kelly keeps 75% of growth; general drawdown law P(V/V0 ≤ x) = x^(2/c − 1) — [A Rational Risk Policy? Why Path Dependence Matters](https://pmc.ncbi.nlm.nih.gov/articles/PMC9955835)
- Volatility targeting (Moreira & Muir, JF 2017): portfolios that "take less risk when volatility is high produce large alphas, substantially increase factor Sharpe ratios" (~25% Sharpe increase for the market factor in-sample); later work (Cederburg et al. 2019) finds the gains do not survive out-of-sample estimation and Barroso & Detzel (2021) that transaction costs can erode them — [NBER w22208](https://www.nber.org/papers/22208)
- Kaiko: Binance's average spot trade size is "below $1,000" (Dec 2025) — [Kaiko Binance report (PDF)](https://resources.kaiko.com/hubfs/Liquidity%20Flywheel%20Drives%20Binance%20to%20300%20Million%20Users.pdf)
- Fee floor for the arithmetic: 0.10%/0.10% Regular, 0.075% with BNB — [Binance Fee Schedule](https://www.binance.com/en/fee/schedule)

### Inferences
- Arithmetic of the edge (assumptions: e = expected net return per trade after fees and slippage, n trades/year, f = fraction of account per trade, non-compounded). With 2-4 trades/week, n ≈ 104-208. Expected annual gain ≈ n·e·f·capital.
  - e = 0.5%, f = 25% (four concurrent positions): $1,000 → $130-$260/yr; $5,000 → $650-$1,300; $20,000 → $2,600-$5,200.
  - e = 1.0%, f = 25%: $1,000 → $260-$520; $5,000 → $1,300-$2,600; $20,000 → $5,200-$10,400.
  - Fully invested every trade (f = 100%) multiplies these by four but makes a 50% drawdown roughly a coin flip (see Kelly below). At $1,000 the edge pays a few hundred dollars a year at best, i.e., less than the owner's time; at $20,000 it is a meaningful side income only if the edge is real and sizing is disciplined.
- Gross edge needed: a 0.5% *net* edge on alts means ~0.9% gross at the app's 0.40% round-trip cost assumption, or ~0.7% at Binance's actual 0.15-0.20% fee round trip plus a few bps of slippage at these order sizes.
- Statistical visibility: if per-trade return SD is ~10% (multi-day holds in coins with 4-6% daily vol), detecting e = 0.5% at t = 2 needs n ≈ (2·0.10/0.005)² = 1,600 trades; e = 1% needs ~400. At 2-4 trades a week that is 2-15 years. The ledger's "beats random entries" test is therefore weak evidence for any single strategy at these frequencies; pooling strategies, using the random-baseline variance reduction the app already has, and trading more coins per signal (more trades, not bigger ones) are what shorten the wait.
- Sharpe and drawdown expectation: per-trade Sharpe ≈ e/σ ≈ 0.05-0.10; annualised over 104-208 trades ≈ 0.5-1.4. With alt annualised vol around 80-100% and a 25-50% average exposure, portfolio vol is 20-50%/yr and multi-month drawdowns of 20-40% are ordinary, not evidence the edge died. The owner should pre-register a drawdown that *would* count as failure (e.g., exceeding the 5th percentile of the random-baseline drawdown distribution).
- Kelly-consistent sizing: f* = e/σ² per trade. e = 0.75%, σ = 10% → f* = 0.75 of the account; half Kelly ≈ 37%. e = 0.5%, σ = 12% → f* ≈ 0.35; half Kelly ≈ 17%. So 15-40% of the account per position is the Kelly-consistent band, and overestimating e by 2× (the usual backtest optimism) turns half Kelly into full Kelly. Volatility targeting (size ∝ 1/ATR) is the practical implementation and already matches the app's ATR-based stops; the Moreira-Muir caveat is that the Sharpe gain is uncertain out-of-sample, so treat it as drawdown control, not as alpha.
- Concurrent positions dominate: four 25% positions in correlated alts behave like one 100% position when BTC moves; the regime filter the app already has is the main diversifier. Cap total exposure (sum of position notionals) rather than per-position size alone.
- Realistic headline: the population base rate is that most retail crypto users lose, and the measured behaviour (momentum chasing, over-trading after adoption) is the mechanism; a rules-based, fee-aware, sized system with a kill switch avoids those specific failure modes but does not by itself create an edge. The paper ledger's job is to show the edge exists before capital follows it.

### Gaps
- The "73-81% of users lost money" figure often attributed to BIS Bulletin 69 could not be verified in the fetched text (only "a majority"; the PDF did not parse); treat it as unconfirmed.
- No 2024-2026 account-level study of *spot crypto* retail P&L (exchange or broker disclosures) was found before the search budget ran out; the Polymarket and simulation studies are proxies. Hackethal et al.'s return figures were behind the paywall (abstract only).
- No peer-reviewed study of volatility targeting applied to crypto strategies was found.
